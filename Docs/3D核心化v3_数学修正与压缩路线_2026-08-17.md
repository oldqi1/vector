## 1. 已确认成立的框架（不再变动）

- 矢量枪 = 玩家最可靠的**主动**水平定向与空中导向；
- 升空叉 = 水平→垂直转换器；
- 绳线 = 空中修正与约束；
- 落地震荡 = 兑现通道；
- Boss 顶部弱点用**几何入射条件**，不写工具白名单；
- 玩家垂直移动交给**高处绳线锚点**；
- **先记录重复伤害日志，再决定是否做 Ledger**。

### 1.1 文案更正：水平速度来源不止矢量枪

v2 写「矢量枪是唯一水平速度来源」不准确。角槌兽冲锋、动能球、坡面同样是 Source。

正式表述改为：

> **矢量枪是玩家最可靠的主动水平速度供给；敌人与场地也能提供预算。**

这一点很重要——它意味着「不用矢量枪也能玩高度」，玩家可以借冲锋怪的动能做换向，这才是 Source/Converter/Receiver 的本意。

### 1.1 2026-08-17 PIE 后的操作顺序修正

矢量枪先击退、再要求玩家切换升空叉并重新点中高速移动目标，虽然数学成立，但操作上需要追逐二次准星，不应成为基础教学链。Demo 的可控主链改为：

```text
升空叉（建立易读空中目标） → 矢量枪（选择水平去向） → 未来的落点/砸落接收器
```

原来的水平→垂直换向仍然保留，但定位为**反应性高阶链**：借角槌兽、动能球或 Boss 冲锋的已有高速，在其接近时用升空叉改向。PIE 已证实 Boss `preSpeed=1436` 时会得到 `postVh=505/postVz=1158`；平衡修订后，普通低速目标只获得 520 垂直保底，不能自行触发震荡。结果取决于可读的真实入射速度，不是随机数。

首版不通过额外动量保持来强推“枪→叉”组合，因为那会让目标更久地高速离开准星。若未来仍希望支持该顺序，应采用短时同目标锁定/组合辅助，而不是改变物理速度。

## 2. 数学修正（全部采纳）

### 2.1 速度旋转不得再次经过质量换算

**问题**：目标当前速度已经包含矢量枪施加时的质量响应（`speed = impulse / effectiveMass`）。升空叉若再调用 `ComputeMassAdjustedSpeed`（其实现为 `BaseSpeed / max(0.1, mass)`），重型目标会被**质量惩罚两次**。

**修正**：直接旋转当前实际速度。

```text
B    = η · |Vₕ|          η = 0.88（转换损耗）
Vₕ'  = B · cosθ
Vz'  = B · sinθ
```

**低速目标单独走 520 cm/s 保底升空**，并明确承认：**这是升空叉提供的有限能量**，不再声称「完全不创造速度预算」。它低于 600 的落地震荡阈值；保底路径同时收回水平速度。

诚实表述：

> 升空叉主要搬运已有水平动能；对静止/低速目标提供有限的保底升空能量。

### 2.2 v2 表格慢速数据算错

按 v2 自己的公式验算：

```text
s = 800, k = 0.6
Floor(s) = lerp(700, 1100, 800/1200) = 700 + 400×0.667 ≈ 967
```

v2 表格写 850，**错误**；对应高度也不是 3.7m。

修正后（v3 公式，η=0.88，θ=arccos(1−0.6)=66.4°）：

| 情况 | s | B=0.88s | 输出 Vh' | 输出 Vz' | 顶点 |
|---|---|---|---|---|---|
| 静止 | 0 | 0 | 0 | **520 保底** | 1.38 m |
| 慢速 | 800 | 704 | **282** | **645** | 2.12 m |
| 中速 | 1400 | 1232 | 493 | 1129 | 6.5 m |
| 矢量枪推过 | 2400 | 2112 | 845 | 1936 | 19.1 m |

**当前基础保底线固定为 520，不再用 `lerp` 曲线**；专属 `LIFT-VECTOR COUPLER` 的定向砸落才拥有 700 的独立预算下限。

### 2.3 「速度绝不增长」与保底升空矛盾

**问题**：静止目标 `|V_before| = 0`、`|V_after| = 520`，仍然增长，因此必须明确它是工具的有限保底供能，而非能量守恒路径。

**修正后的约束**：

```text
s       = |Vh_before|
B       = η·s
Vz_turn = B·sinθ

if Vz_turn < FloorSpeed:
    Vh_after = 0
    Vz_after = FloorSpeed
    floorUsed = true
else:
    Vh_after = B·cosθ·Vh_direction
    Vz_after = Vz_turn
    floorUsed = false
```

因此旋转路径严格满足 `|V_after| = η·|Vh_before|`；保底路径严格输出 `|V_after| = 520`。800 输入已经高于保底分支，输出 `Vh'=282、Vz'=645、合速度704`，不超过预算。

即：**旋转路径不增长能量；保底路径是明确、有上限、可预测的例外。**

同时**删除隐藏的 0.6ⁿ 衰减**——它难读、难预测，且与冷却和 `AirborneCharge` 功能重复。

防连击改为三重，全部可见：

1. `AirborneCharge = 1`，落地接触 ≥ 0.2s 回充；
2. 冷却 1.1s；
3. 上述能量约束（保底不叠加，同目标已在空中时不给第二次保底）。

### 2.4 砸落弹道符号有误

**标准形式**（与工程内 `ComputeBallisticLaunchVelocity` 实现一致）：

```text
a  = (0, 0, −g)
V0 = (P − Pt − 0.5·a·T²) / T
```

因 `a.z = −g`，Z 项实际是**加上** `0.5·g·T²`。

工程现有实现已是正确形式：

```cpp
OutVelocity = (Target - Start) / FlightSeconds;
OutVelocity.Z -= 0.5 * GravityZCmPerSecondSquared * FlightSeconds;  // g 为负，故为加
```

**关键修正：求解后不得再强行改写 `V_slam.z`**，否则算出的落点与实际落点不一致，预测环就成了骗人的。

正确流程：

```text
1. 先求可行的 T
2. 确认 V0.z < 0（确实是向下砸）
3. 检查速度预算是否够
4. 不可达时：缩近落点重解，或直接拒绝
   —— 不修改 Z 后继续声称能命中原落点
```

#### Demo 的确定性 T 与速度预算

`ComputeBallisticLaunchVelocity` 需要调用方给出飞行时间，因此不能只写“求 T”。Demo 固定采用离散候选求解：

```text
h              = max(0, Pt.z − P.z)
T_natural      = (Vz_now + sqrt(Vz_now² + 2·g·h)) / g
T_upper        = clamp(0.9·T_natural, 0.20, 0.90)
SlamBudget C   = max(|V_current|, 700)

从 T=0.20 开始，以 0.05s 步长枚举到 T_upper：
    V0 = (P − Pt − 0.5·a·T²) / T
    只保留 V0.z < 0 且 |V0| ≤ C 的候选
    选择 |V0| 最小的候选（并列时选更短 T）
```

若原落点无解，则沿 `Pt` 的地面投影到玩家鼠标落点之间，以 `α=0.9、0.8…0.1` 依次缩近重解；仍无解则明确拒绝并显示红色落点环。求解成功后不再修改任何速度分量。

这样砸落与首次升空共用同一个有限例外：当前速度预算不足时最多使用 `700cm/s`，不会凭空出现第二套隐藏冲量。

### 2.5 Boss 冲量条件实际取消了质量

**问题**：`J = m·|Vz| ≥ m·1200` 两边约掉 m，等价于 `|Vz| ≥ 1200`。叫「法向冲量」是错的。

**二选一，不含糊**：

- 若真要检查法向冲量 → 用**固定** `Jmin`（如 `J ≥ 9600 kg·cm/s`），此时轻物需要更高速度，重物更容易破坏；
- 若只想检查速度 → 直接写 `|Vz| ≥ 1200`，**不要叫冲量**。

**推荐后者**（速度阈值），因为它对玩家可读：「砸得够快就能破」。

### 2.6 附加技术约束：井口必须有真实碰撞体

现有 Boss 基于 Character/Capsule。顶部凹井**必须有真实查询碰撞体**（额外 Sphere/Box 组件或独立碰撞代理），不能只改模型外观——否则几何判定形同虚设，入射角算得再准也命不中。

## 3. 伪问题澄清：准星 Pitch 不存在

v2 提出「k 由准星俯仰决定，三档还是连续」。

**当前俯视操作没有独立的准星 Pitch**——鼠标只提供地面投影点。因此「三档还是连续」是伪问题。

正确演进方向：

- **Demo 期**：固定标准换向角 `k = 0.6`；
- **后续**：通过**鼠标落点反求弹道**，而不是让玩家去调一个抽象的 Pitch 数值。

这符合当前“结果式瞄准”原则：玩家声明希望发生的落点，系统用统一弹道参数反求可行速度，而不是要求玩家操作抽象 Pitch 数值。

### 4.1 裁决 2 的前置改造（已核实必要性）

```cpp
// VectorGravityHookComponent.cpp:280 —— 当前墙面锚点检索
const FVector End = Start + AimDirection.GetSafeNormal2D() * HookRangeCm;
```

`GetSafeNormal2D()` 把方向压回水平面，**玩家永远勾不到高处锚点**。

## 5. 压缩后的实施路线（顺序已修正）

v2 的 44h 超出可控范围，且**把 Boss 排在高度房之前是错的**——应先验证高度房。

| 步 | 内容 | 验收信号 | 工时 |
|---|---|---|---|
| 1 | **固定 k=0.6 的升空换向** | 日志含 `PreSpeed / B / Vₕ' / Vz' / floorUsed`；旋转路径 `\|V\|` 不增长；静止目标走 520 保底 | 4h |
| 2 | **空中目标影子 + 落点环 + 真实碰撞预测** | 相邻弹道采样点之间做 Capsule/Sphere Sweep，以第一次阻挡为落点；20 次预测误差 < 120cm | 6h |
| 3 | **一次空中砸落** | 求 T → 校验 `V0.z<0` → 校验预算 → 不可达则缩近或拒绝；`FallSpeed` 与 `LandingShock` 配对出现；同帧全部伤害来源可见 | 5h |
| 4 | **环境换向器 + 手工 HeightShelf 两路线** | 新增一个读取入射速度的通用环境换向器；环境路线与工具路线各自可完成；删除高度后至少一条消失、主合同仍可完成 | 8h |
| 5 | **通过后**才做 Boss 顶部井口 | 真实碰撞体 + `φ < 26.5°` + `\|Vz\| ≥ 1200`；至少 2 条不同物理链路触发成功，第 3 种为加分项 | 6h |
| 6 | **最后**加高处绳线锚点 | 绳线墙面检索与牵引三维化；玩家可勾高处锚点上层；绳线可改变空中目标轨迹和落点 | 7h |
| | | **合计 36h** | |

### 关键顺序原则

- 第 1–4 步构成**一条完整可验证的高度电路**，做完即可判断 3D 是否成立；
- 第 5 步（Boss）依赖第 4 步验证通过；
- 第 6 步（玩家垂直位移）排在最后，因为它需要绳线三维化改造，风险最高；不再以旧稿“离地次数/死亡占比”作为制作理由。

若时间只够前 4 步（23h），仍能得到一条完整高度电路，只是玩家自己还不能用工具主动上到 650cm 上层。当前 30h Demo 预算只承诺前 4 步；Boss 井口和高处绳线必须由 HeightShelf 实测结果决定，不预先承诺完成。

## 6. 手工 HeightShelf 配置

| 角色 | 内容 |
|---|---|
| 动能源 | 冲锋怪（角槌兽）或动能球 |
| 转换器 | 通用环境换向器 / 升空叉 |
| 接收器 | 下层怪群 / 上层结构点 / 裂解墙 |
| 路线 A | 环境升空路线（角槌兽/动能球进入通用环境换向器，**不需要升空叉**） |
| 路线 B | 工具换向路线（矢量注入 + 升空叉 + 定向砸入低层怪群） |

**路线 A 不依赖升空叉**，这样才能验证「场地也能提供预算」这一表述。

### 6.1 环境换向器的最小合同

普通可行走坡道不能作为可靠实现前提：CharacterMovement 可能把速度持续投影到地面，在坡顶恢复为水平速度。首版新增一个通用速度换向区域/出口：

- 只读取进入者的世界速度、入射方向与作者配置的出口方向；
- 只对 `IsImpulseDriven()` 的可移动目标生效，站着走进去不发射；
- 使用与升空叉相同的 `η` 预算限制，但由场地出口方向决定旋转平面；
- 不识别怪物类型、工具类型或任务阶段；
- 每个目标离开区域后才可再次触发，防止单帧重复消费；
- 日志包含 `sourceSpeed / exitDirection / resultVelocity / check=PASS`。

它可以表现为坡顶导流轨、重力喷口或机械弹射板，但代码合同只有一个。删除该换向器后，路线 A 必须消失。

删除测试已经进入 PCG 数据 Gate：移除 `EnvironmentRedirector` 后路线数 `2→1`，保留工具路线；禁用 `LiftFork` 后路线数 `2→1`，保留环境路线；两者都移除时高度高价值路线 `2→0`。遭遇清场账本只登记敌人，不登记装置，因此单独删除任一 Converter 不会锁门，仍可用较慢基础战斗完成主合同。

### 7.1 落点预测的碰撞要求

影子只需向下查询当前地面；**落点预测不能只解 `Z=地面高度`**。预测器必须沿 `SampleBallisticPosition` 的相邻采样点做 Capsule/Sphere Sweep，并使用实际目标的碰撞半径，以第一次 `WorldStatic` 阻挡作为预计落点。这样才能正确处理墙、斜坡、上层平台、天花板和不同地面高度。
